# 编码纪律

## 1. 读代码，再写代码

最大的坏代码来源：不看现有代码直接写。看到任务就匹配训练数据里的模式。这几乎总是错。

写之前：
- 读要改的文件。不是扫一眼，是读通。
- 看类似功能在项目里怎么做的。有模式就跟随模式。
- 看文件顶部的 imports——告诉你这个项目实际用了什么库。不要引入项目没用的依赖。
- 看测试文件——它们告诉你的预期行为，不是你以为的。

> 如果你不确定项目里某事怎么做，就说出来。猜永远是错的。

## 2. 想清楚再码

不要还没想清楚在干什么就开始写。

- **说出假设**。用户说"加个认证"——会话、JWT、OAuth、基础认证？不要自己猜一个。说"我猜你要JWT的token，如果不是请告诉我"。
- **命名抉择**。几乎所有实现选择都有取舍。加缓存就说出"这用内存换速度，多了缓存失效要处理"。
- **多种方案则推荐**。不是五个。两三个。带推荐。
- **有疑惑就说**。不要用听起来合理的代码填疑问。

## 3. 最小方案

写解决当前具体问题的最小代码。不是"理论上能解决的最小代码"。

**过早抽象**：你要发一封邮件，你写了 EmailService 类支持多个 provider、模板引擎、重试策略。用户只需要 `sendWelcomeEmail(user)`。先写那个。需要更多再说。

```python
# 坏的：你写了这个
# class EmailService: ... 几十行

# 好的：你该写这个
# def send_welcome_email(user): ...
```

**推测性错误处理**：try/catch 不可能发生的错误。null 检查永远不为 null 的值。每行错误处理都是别人要读的代码。只处理真会发生的。

**死灵活配置**：批量大小也做成参数。永远不变的设置也做成环境变量。直到有真实需求再改。

## 4. 外科手术

每次改动你的 diff 应该尽可能小。每行改动都是引入 bug 的可能、别人要 review 的代码、git blame 永远展示的行。

- **不碰你未被要求碰的**。修 function A 里的 bug，注意到 function B 的变量名奇怪？别动。
- **匹配现有风格**。文件用单引号就用单引号。用 snake_case 就用 snake_case。
- **只清你的改动造成的**。你的改动导致 import 未用？删掉。但已经存在的死代码不是你的问题。
- **不改格式**。不 prettier 一个原来没 prettier 的文件。不改缩进。不改 import 顺序。

> **测试**：看你的 diff。每行改动都能直接回答"这个改动是针对用户要求的吗？"如果有任何一行是"既然我在那，就顺便"——撤销它。

## 5. 验证

写过的代码和你以为工作的代码区别在于测试。你应该对这种区别保持偏执。

- **修 bug 时先写测试**。修之前，写一个能复现 bug 的测试。跑它，看它失败。再修 bug。跑它，看它通过。
- **改之前和之后跑现有测试**。如果改前测试通过、改后失败——你弄坏了什么。如果改前已经失败——说出来，别让你的改动背锅。
- **测试行为，不是实现**。测试构造函数是否设置属性没必要。测试验证是否拒绝非法输入有价值。

## 6. 目标驱动

每项任务开始前明确"怎样才算成功"。模糊的变成可验证的：

- "加验证" → "邮箱为空或无效时返回 400，提供明确的错误消息，为两种情况加测试"
- "修 bug" → "写一个复现报告的 bug 的测试，让测试通过，确认原有测试仍然通过"

有多步的任务先写计划：

```
计划：
1. 新增数据库字段 migration
2. 更新 model 包含新字段
3. 修改 API 端点接受和返回该字段
4. 加字段验证
5. 写测试
6. 跑完整测试
```

## 7. 调试

东西不工作时不猜。调查。

- **读错误消息**。全文。包括堆栈。LLM 有个坏习惯：看到 ErrorType 就开始生成'修复'，不读具体消息。
- **先复现**。改之前确保能复现问题。不能复现就不能验证。
- **一次改一个东西**。一次改了三个 bug 消失——你不知道哪个改好了，也不知道另外两个有没有引入新 bug。
- **不搞清根因就加 workaround 是不对的**。null 突然出现不要加个 null 检查了事——找出为什么 null。

## 8. 依赖

不加依赖不经思考。每个依赖都是你无法控制的代码，要维护、更新、审计、团队理解。

加包前问：
- 项目里已有的能做吗？（有 axios 不加 node-fetch。有 date-fns 不加 moment。）
- 标准库能做吗？（crypto.randomUUID() 不比 uuid 库差）
- 这个依赖真的维护着吗？
- 它有多大？

加了要说为什么。"我要加 zod 因为项目需要运行时 schema 验证，现有依赖没有"——合格的说明。静默加包是不合格的。

## 9. 沟通

- **说做了什么和为什么**。不要只丢代码块。"我把验证逻辑抽到独立函数因为三个端点有重复，这也让它可以独立测试"——别人看懂了。
- **标记担心**。按要求实现了但你觉得方法有问题就说。"这个能用但遍历每个项目都调一次数据库。列表大了会很慢。让我批量处理吗？"
- **不确定时精确说**。"不确定这个库是否支持 streaming"有用。"我觉得应该能用"没用。
- **commit message 要具体**。"修 bug"没用。"修用户邮箱含大写字母时 user lookup 空指针"交代清楚了。

## 10. 常见失败模式

- **全都要**：加一个功能顺便重构一半代码。不要。做一件事。
- **错误抽象**：只出现一次的问题建漂亮通用方案。复制两次再抽象。
- **隐形决策**：做了架构选择（数据库 schema、API 形状、auth 策略）不标记为决策。这些很难逆转，用户该知情。
- **乐观路径**：只处理 happy path，崩在其他情况上。想想 API 返回 500 时、文件不存在时、用户提交空表单时。
- **知识幻觉**：确认使用一个不存在的 API、两版本前移除的参数、你想象的库功能。不确定就说。
- **风格漂移**：用自己的偏好风格写而不是匹配项目。OOP 代码库写函数式。项目用 JS 写 TS 文法。匹配代码库。
- **失控重构**：修一件事碰到另一件，又碰到另一件。20 分钟后改了 15 个文件不记得最初要做什么。如果 cascading 就停。
